## 一、编译阶段遇到的问题：Buildroot 下载 dl 库经常 404

编译 Buildroot 的过程中，经常卡在下载依赖包阶段。部分依赖源已经失效，或者网络访问不稳定，导致自动下载失败。

今天遇到或处理过的依赖包括：

```text
libpng Target
dhrystone
fio
host-libjpeg
host-libpng
UnixBench
```

当时的状态大致如下：

```text
libpng Target：已通过
dhrystone：已通过
fio：已通过，或者已经跳过
host-libjpeg：已完成安装
host-libpng：曾经是卡点，后续处理通过
Host 工具链：基本完成
基础图形库 libpng/libjpeg：完成
性能测试工具 UnixBench：卡点，最后选择快速跳过
```

### 问题原因

Buildroot 在编译过程中会从外部网络下载源码包。老 SDK 经常会遇到下面几类问题：

```text
1. 下载链接失效
2. 上游文件被移动
3. 镜像站没有对应版本
4. 网络访问失败
5. 某些包版本太旧
```

这些问题不一定是代码错误，而是老 SDK 常见的构建环境问题。

### 解决方式

当自动下载失败时，我采取了几种处理方式：

```text
1. 手动下载源码包
2. 将源码包放入 buildroot/dl 目录
3. 必要时手动解压或调整文件名
4. 对非核心组件选择跳过
```

Buildroot 的下载缓存目录通常是：

```text
buildroot/dl/
```

如果某个包下载失败，可以先看日志中需要的文件名，然后把手动下载的文件放入：

```text
buildroot/dl/
```

再重新执行编译。

## 三、打包阶段遇到的问题：recovery.img 缺失

编译完成后，执行固件打包：

```bash
./build.sh updateimg
```

最开始出现了如下错误：

```text
Add file: ./Image/recovery.img
Error:<AddFile> open file failed,err=2!
```

这里的 `err=2` 表示：

```text
文件不存在
```

也就是说，打包工具根据 `package-file` 的清单想把 `recovery.img` 加入 `update.img`，但实际没有找到这个文件。

### 定位过程

先搜索 `package-file`：

```bash
grep -R "package-file" -n build.sh mkfirmware.sh tools device 2>/dev/null | head -n 100
```

再搜索 `recovery.img`：

```bash
grep -R "recovery.img" -n build.sh mkfirmware.sh tools device 2>/dev/null | head -n 100
```

最终定位到实际使用的打包清单：

```text
tools/linux/Linux_Pack_Firmware/rockdev/package-file
```

里面原本存在：

```text
recovery        Image/recovery.img
```

但是当前构建流程并没有生成 `recovery.img`。

### 解决方式

将 `recovery` 这一行注释掉：

```text
#recovery Image/recovery.img
```

最终 `package-file` 中和打包相关的内容变成：

```text
# NAME		Relative path
#
#HWDEF		HWDEF
package-file	package-file
bootloader	Image/MiniLoaderAll.bin
parameter	Image/parameter.txt
#trust		Image/trust.img
uboot		Image/uboot.img
misc		Image/misc.img
#resource	Image/resource.img
#kernel		Image/kernel.img
boot		Image/boot.img
#recovery Image/recovery.img
rootfs		Image/rootfs.img
oem		Image/oem.img
userdata	Image/userdata.img
backup		RESERVED
#update-script	update-script
#recover-script	recover-script
```

为了避免 `build.sh` 重新链接或覆盖配置，还同步修改了：

```text
tools/linux/Linux_Pack_Firmware/rockdev/rk356x-package-file
```

因为我的当前目标不是发布量产固件，而是：


## 五、打包后 update.img 一开始只有 28M

注释 `recovery` 后，`update.img` 成功生成，但是最开始看到它只有：

```text
28M
```

这明显不合理。

因为当时 `rockdev` 中已有：

```text
boot.img      23M
uboot.img     4.0M
rootfs.img    420M
oem.img       17M
userdata.img  4.3M
```

如果完整打包，`update.img` 至少应该大于：

```text
450M
```

所以当时判断：

```text
28M 的 update.img 不能烧录
```

### 当时的怀疑

当时怀疑过几个方向：

```text
1. rootfs.img 没有打进 update.img
2. Image/rootfs.img 没有被正确链接
3. Windows 看到的是软链接大小
4. build.sh updateimg 使用的不是最新文件
5. update.img 是旧的残留文件
```

后来通过日志确认，`rootfs.img` 实际已经加入了打包流程。

关键日志如下：

```text
Add file: ./Image/rootfs.img
rootfs,Add file: ./Image/rootfs.img done,offset=0x1b6e800,size=0x1a36a000,userspace=0x346d4
Add file: ./Image/oem.img
oem,Add file: ./Image/oem.img done
Add file: ./Image/userdata.img
userdata,Add file: ./Image/userdata.img done
```

这说明：

```text
rootfs.img 已经成功打包进 update.img
```

### 为什么后来又正常了

目前还不能完全确定 28M 的原因，但从过程看，大概率与以下因素有关：

```text
1. 之前生成的是旧的 update.img
2. 第一次打包在 recovery.img 失败前没有完整完成
3. 修改 package-file 后重新打包才真正加入 rootfs.img
4. rockdev 里的部分文件是软链接，Windows 文件管理器显示容易误导
5. Linux 下重新确认和重新打包后，最终固件恢复正常
```

后续经验：

```text
不要只看 Windows 文件管理器中的大小
不要直接相信第一次生成的 update.img
必须用 updateimg.log 确认 rootfs 是否加入
必须用 ls -lh 确认最终 update.img 大小
```

## 六、软链接问题

在 Windows 文件管理器中查看 `rockdev` 目录时，发现很多镜像文件显示只有：

```text
1 KB
```

这容易让人误以为镜像坏了。

后来确认，这些文件很可能是 Linux 软链接。Windows 浏览 Linux 文件系统时，显示的是软链接本身大小，而不是目标文件真实大小。

### 正确查看方式

在 Linux 下使用：

```bash
ls -lh rockdev/*
```

或者跟随软链接查看真实文件大小：

```bash
ls -lhL rockdev/*
```

其中 `-L` 表示跟随软链接。

今天最终看到的真实文件大小是：

```text
MiniLoaderAll.bin   455K
boot.img            23M
misc.img            48K
oem.img             17M
parameter.txt       488B
rootfs.ext4         420M
rootfs.img          420M
uboot.img           4.0M
update.img          后续重新打包后应为几百 MB
userdata.img        4.3M
```

经验：

```text
以后检查 SDK 编译产物，一律在 Linux 终端下看，不要只看 Windows 文件管理器。
```

## 七、确认 rootfs.img 被打包进 update.img

为了确认 `rootfs.img` 是否真的进入 `update.img`，查看了 `updateimg.log`：

```bash
grep -n "Add file:" updateimg.log
```

关键结果：

```text
Add file: ./Image/rootfs.img
rootfs,Add file: ./Image/rootfs.img done
```

这说明 `rootfs.img` 已经进入 `update.img`。

如果以后再次遇到类似问题，需要检查：

```bash
grep -n "rootfs\|recovery\|FAILED\|Error" updateimg.log
```

判断标准：

```text
如果看到 Add file: ./Image/rootfs.img done，说明 rootfs 已经打包。
如果 update.img 只有几十 MB，要怀疑是不是旧文件或打包未完成。
如果 update.img 大于 450M，基本符合预期。
```

## 十一、今天得到的经验

今天最大的经验是：

```text
Rockchip SDK 编译不是一步到位的黑盒流程。
```

它实际由几部分组成：

```text
Buildroot 生成 rootfs
Kernel 生成 boot.img
U-Boot 生成 uboot.img
mkfirmware.sh 收集分散镜像
package-file 描述 update.img 打包清单
Linux_Pack_Firmware 工具生成 update.img
RKDevTool 烧录 update.img
```

今天真正看明白了几个关键点：

```text
1. rootfs.img 是系统根文件系统，非常关键
2. update.img 只是最终打包格式，不是唯一烧录方式
3. 分散镜像也可以烧录
4. package-file 决定 update.img 包含哪些分区
5. recovery.img 缺失会导致 update.img 打包失败
6. 软链接在 Windows 下显示大小可能误导
7. 判断 update.img 是否完整，必须看日志和最终大小
```
